## MAJOR items

1. **Bind authorization to the managed project before using the privileged service client.** `app/api/admin/users/[id]/status/route.ts:10,31` accepts `requirePlatformAdmin(req)` and then switches to `getAdminMedplum()` in `lib/fhir/admin-service.ts:572`. The existing guard only checks `auth/me.membership.admin === true`; it never checks the caller's project against the application project's identity. With an admin token for a different project on the same Medplum server, a caller can PATCH a known application Practitioner ID and toggle its membership using the application's credentials. The guard's weakness predates this diff, but the new endpoint inherits it. Validate the authenticated project and intended platform-admin authority before mutation, and explicitly scope target membership selection to that project. Add a negative test using another project's admin token. Ordinary clinic staff without membership.admin are denied; that does not address this cross-project case.

2. **The purported full membership scan fetches only one page.** `lib/fhir/admin-service.ts:448-458` uses `searchResources(..., { _count: '500' })`. Installed SDK source (embedded `client.ts` in `node_modules/@medplum/core/dist/esm/index.mjs.map`, lines 1796-1809) converts one search bundle to an array; it does not follow next links. With more than 500 memberships, a Practitioner returned by the independent Practitioner query can have a membership outside this page: an inactive account is incorrectly marked Active, omitted from the Deactivated filter, and both status operations fail with a generic 500. Iterate `searchResourcePages` or otherwise retrieve all relevant memberships, scoped to the managed project. Preserve unknown/no-login status rather than treating an incomplete lookup as active. Test a target beyond the first page.

3. **The security behavior has no executed end-to-end evidence, and the new test cannot establish existing-session revocation.** `e2e/tests/admin.spec.ts:211-239` only attempts fresh login after deactivation; any non-2xx (including infrastructure failure or rate limiting) passes that assertion. It never signs in the fake user first, keeps its session, and asserts an authenticated clinical request is rejected after deactivation. It also omits anonymous/non-admin/cross-project authorization tests. Capture a working fake-user session before deactivation; assert a specific auth-denial response for fresh login and retained-session access, preserve roles/profile/history, and verify access after reactivation. Run the opt-in admin audit against this worktree and the required `e2e/scripts/check-all.sh <label>` gate before marking Task 6e done. The default gate excludes admin.spec.ts unless opted in.

## Checks and non-findings

- `ProjectMembership.active` is the appropriate field. Medplum v5.2.8 `getInactiveReason` checks `membership.active === false`; `context.ts:272-302` reloads the membership and rejects inactive authenticated contexts, and `oauth/token.ts:340-347` rejects refresh grants. No extra app token-revocation mechanism is required for Medplum-backed operations. The added exact inactive-error mapping is compatible with the server's OperationOutcome text.
- Self-check: for the exact targeted membership profile `Practitioner/<id>`, the route blocks deactivation before writing. A `superAdmin` project does not itself bypass that comparison: official `auth/me.ts` resolves the profile from `membership.profile`. Patient, RelatedPerson, Bot, and ClientApplication profiles cannot be that same Practitioner reference merely by sharing its UUID, so the resource-type condition alone is not a demonstrated self-deactivation bypass. Cross-project/multiple-profile identity cases still require explicit project/user policy and tests; do not claim a blanket guarantee based only on one Practitioner fixture. The e2e currently fails rather than exercises protection if its admin is not a Practitioner.
- Clinic separation: status deliberately applies to project-wide login access across assigned clinics; it should not be restricted to a single clinic assignment. It does not modify clinical resources, clinic identifiers, PractitionerRole assignments, or Firebase Storage. The authorization/project boundary in MAJOR 1 remains necessary.
- Edit/delete: deactivation leaves `Practitioner.active` intact, so the existing archive filtering continues to mean deletion, and deactivated Practitioners remain editable/deletable. Existing delete logic still removes matching memberships. However, both user detail and the detail returned after profile edit now require a successful membership search; a service policy that previously allowed Practitioner/role operations but not membership search will now fail those reads and can return failure after an edit has already persisted. Ensure the deployed service account has membership search/update permission. No direct composer, Lab, or POCT changes were found.
- Badge/filter paths and async Next searchParams handling are consistent with the current routing helpers. Confirmation dialogs precede both status changes, and self-action hiding is mirrored server-side. SDK updateResource invalidates membership search caches; the default Node SDK cache time is zero, so no reproducible singleton-cache bug was found.
