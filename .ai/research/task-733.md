# Task 733 CSRF origin review

- [Next.js 16 Proxy](https://nextjs.org/docs/app/api-reference/file-conventions/proxy) runs before App Router route handlers. The installed 16.4.5 server constructs the Proxy URL from the request protocol and may substitute its internal hostname, so use its protocol and the ingress `Host` separately. [Vercel documents `Host`](https://vercel.com/docs/headers/request-headers#host) as the domain accessed by the client, including assigned preview and custom domains. The CSRF guard should not use an incoming `X-Forwarded-Host` as independent authority.
- [Vercel's generated URL formats](https://vercel.com/docs/deployments/generated-urls) describe the hostname convention. A regex matching that convention is not a deployment identity check. Let the active preview use the normal same-origin path. Use an exact origin for an intentional cross-origin integration. Apply that same rule to sibling custom domains to preserve their CSRF boundary.
- The [Fetch standard](https://fetch.spec.whatwg.org/#origin-header) permits `null` as the serialized origin and defines browser-controlled request headers, CORS-safelisted methods and content types, and preflights. [Fetch Metadata](https://www.w3.org/TR/fetch-metadata/#sec-fetch-site-header) distinguishes same-origin from same-site requests and considers redirects. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) recommends exact origin checks and blocking simple requests that lack trusted source evidence. This app does not grant cross-origin CORS access to protected mutation routes. Headerless API clients using JSON POST or PUT/PATCH/DELETE can therefore retain their existing behavior. A caller using browser-simple POST must establish its source.
- [React 19 Server Functions](https://react.dev/reference/rsc/server-functions) have a framework-managed entry point. The consultation composer uses relative `/api` requests, which go through this Proxy. This review does not modify the composer or Server Function handling.
- References checked for the clinical integration boundary include the [Medplum 5.2.8 release](https://github.com/medplum/medplum/releases/tag/v5.2.8), [FHIR R4 REST API](https://hl7.org/fhir/R4/http.html), and [DICOM PS3.18 Web Services](https://dicom.nema.org/medical/dicom/current/output/chtml/part18/ps3.18.html). Existing device and webhook exemptions retain their route-specific authentication.
