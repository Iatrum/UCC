## Boundary and inventory

Use a separately managed staging Medplum instance (pin and attest server 5.2.8 image digest, PostgreSQL, Redis, binary store, database credentials and backups), with its own **non-superAdmin** clinical Project. Operator superAdmin tooling is private and separate (D20). Never put fake clinic staff in the operator project. A different Project on the production instance is not the proposed environment boundary. Keep a four-clinic fake fixture set with clinic identifiers on every clinical resource; project isolation does not solve within-project clinical isolation.

Use an independent Firebase project, Firestore database and Storage bucket, restricted staging service identity and browser config. Firebase Storage stays. No production service account, application-default credentials, bucket, exports, database snapshots, patient documents or copied patient data. Verify actual Admin SDK project/bucket (including ADC resolution) and browser configuration agree; absence of an explicit credential must fail preflight rather than silently fall back. If an approved no-cost isolated Firebase environment is unavailable, mark durable draft/upload verification BLOCKED; do not call local-only fallback a persistence pass or enable billing here.

Separate domains/cookies, auth clients, receiver keys, CORS, issuer and redirect URIs from production. Cookie domain must not span staging and production; use a disjoint domain or host-only cookies with dedicated staging session material. Use Task 7 network principles: private backing services/operator paths, controlled browser API gateway, closed aliases, authenticated device ingress. Do not open public dev server/database/cache ports. DNS, TLS, costs/quotas and resource ownership remain user decisions; no paid resources may be created by this round.

Record a sanitized manifest: Git commit/build ID, pinned runtime and dependency versions (Next 16.2.1 / React 19.2.6 intended app; verify lockfile), image digest, staging-only origins, Medplum clinical project/client IDs, clinic tenant references, Firebase project/bucket IDs, runner identity and fixture namespace. Store secret values separately with least privilege; never in manifest, logs, PRs, screenshots or shell arguments. Browser NEXT_PUBLIC configuration is build-time: rebuild with staging public values, and rebuild separately for any later production configuration.

## How gates will run

Today's local D22 regression gate remains `NODE_OPTIONS=--max-old-space-size=3072 e2e/scripts/check-all.sh <label>` on ai-work, against the single local dev server :3210 / Medplum :8113. It records lint, build, 22/23 baseline (only known-bug summary fails), clinic check 0. This is application regression evidence only; it does not validate staging, network lockdown or clinical authorization. Before each local gate inspect orphaned vitest workers; do not start another dev server or change Tradebot.

Future staging runner: dedicated machine/container/workspace with independently loaded secret files, no copied local browser storage state, serialized jobs and reports outside the app watcher. Build/start the exact reviewed commit with the manifest; use a production-mode Next build for deployment behavior. Do not run a second server on this shared box. `build:ci` deliberately skips env validation, so run the reviewed full config/identity preflight as a separate required step; current `validate-env` alone checks presence/shape, not safe targeting. Do not execute root `test:e2e*` scripts (production-domain defaults).

The adapter must bind app MEDPLUM_BASE_URL, browser NEXT_PUBLIC_MEDPLUM_BASE_URL, e2e MEDPLUM_URL, UCC_BASE_URL, auth project/client and Firebase config to the same manifest. Their URL values can differ internally/externally only with an attested mapping to the same isolated services. Current admin spec, seed and containment tests have localhost guards, and clinic check is incomplete. Port-forwarding staging to localhost on this box or weakening those guards is not an acceptable shortcut. Port/adapt each test in a separate reviewed change, retaining production rejection.

Run ordered phases: safe-target preflight; lint/types/build; staging-only fixture checks; browser workflows (registration, triage, note signing, composer hydration/local-only and durable save, medication/document/billing paths); fake lab ingestion and Lab tab display; Firebase upload/download and clinic denial tests; admin denial/deactivation; authorization matrix below. Browser/admin/storage negative tests must use staff identities, never an all-powerful client as proof. Keep results in Lab only; no manual entry or critical warning in composer; POCT ordering must fail offline and succeed only with an online simulator. Assert receiver missing/wrong/unconfigured keys fail closed and valid fake delivery works; per-device clinic matching remains a separate prerequisite, not solved by shared keys.

For results: local expected baseline is 22/23, not blanket tolerance for any failure. Current compare.mjs accepts a missing baseline and can overlook newly added failing tests: the staging adapter MUST reject missing/malformed baselines, attest the approved baseline identity/hash against its manifest, and reject every failed/skipped/missing required test except the exact explicitly approved named exception. Added tests are required to pass; an absent baseline or previously unknown failing test cannot produce success. Capture test names, tested commit, origin/project attestation booleans, duration and sanitized assertion counts. On staging, explicitly classify the existing known-bug summary; every previously passing probe must pass, and infrastructure skips cannot be reported as passes. Separate durable Firebase tests from deliberate persistence-unavailable tests; require an actual save/reload read-back and upload/download round-trip. Clinic security acceptance must cover direct FHIR read/search/count/history/vread/includes/batch/transaction, unauthorized create/update/move/delete, Firebase and admin-client routes across fake clinics A/B; current identifier checker is insufficient. Require staff-identity cross-clinic DELETE denial through direct FHIR and applicable app routes, independently verifying the target remains intact. The clinical-isolation plan is outstanding (BACKLOG); its reviewed acceptance matrix is a prerequisite before broader staging use.
