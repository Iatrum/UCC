# PLAN — clinic clinical isolation

Status: plan only, not built. Full findings behind every claim here: `.ai/research/clinic-isolation.md`. Read that first — the summary is: a parameterized, compartment-based `AccessPolicy` for exactly this problem already exists in the repo and is wired into the staff-invite flow, but the rollout is incomplete (2/10 local non-admin memberships have no policy at all and get Medplum's legacy full-access fallback; ~45% of sampled Encounters are missing the `meta.accounts` field the policy's criteria depends on; reassigning a practitioner's clinic doesn't re-sync their policy parameters). This plan **completes and verifies that existing design**, closes the gaps found while reading it, and adds a migration path — it does not invent a new tenant model.

## Data model (no change, confirmed existing)

- **Tenant boundary = `HealthcareService` "clinic account"**, one per clinic, `identifier: clinic|<slug>`, resolved via `lib/fhir/clinic-tenancy.ts:resolveClinicTenant`. This is the resource `%clinicAccount` substitutes to.
- **`Organization`** (also `identifier: clinic|<slug>`) is the clinic's identity/branding/module-toggle record (`lib/module-settings.ts`) and what `%clinicOrganization` substitutes to. Not the compartment boundary itself.
- **Compartment membership = `meta.accounts` on the resource**, set via `POST .../$set-accounts {accounts:[{reference:"HealthcareService/<id>"}], propagate:true}` (`clinic-tenancy.ts:assignResourceToAccountReferences`). This is what `_compartment=%clinicAccount` actually filters on — confirmed live (`_compartment=HealthcareService/<id>` is a working search parameter on this server; `meta.accounts` is the field name on this server version, 5.2.15).
- **`identifier: clinic|<slug>`** on a resource is a separate, app-level display/filter convenience (`withClinicIdentifier`) used for UI queries like `getTriageQueueForToday`. It is **not** a security boundary — it's a plain searchable field any AccessPolicy-governed client can set if it has `update` on that resource type, and it is not what the compartment criteria reads. Keep both fields in sync going forward (they answer different questions: "what does the UI show" vs "what can this token touch"), but never treat the identifier as the enforcement mechanism in a security review.
- **Staff → clinic = `PractitionerRole{practitioner, organization}`**, one row per clinic a practitioner works at (already correctly supports multi-clinic — `assertClinicAssignment` checks "any matching role", not "the first one"). This drives the app-level clinic switcher/guard.
- **Staff token → clinic data = `ProjectMembership.access[]`**, one entry per clinic, each `{policy: {reference: AccessPolicy/<clinic-staff-policy-id>}, parameter: [{name:"clinicAccount", valueReference:HealthcareService/<id>}, {name:"clinicOrganization", valueReference:Organization/<id>}]}`. Multiple `access[]` entries combine (union), per Medplum's multi-tenant guide — this is the correct mechanism for multi-clinic staff, already used correctly by `withClinicMembershipAccess` for a single clinic; extending to N is additive, not a new mechanism.

## Phase 0 — verify before touching any real membership (no code change, blocks everything else)

Two empirical questions this research session could not answer with the time/safety budget available, both必须 be answered with a disposable-identity test (same pattern as Task 5b: throwaway fake Practitioner/Organization/HealthcareService/ProjectMembership, known fake password, deleted in a `finally`, never touching `doctor@ucc.local` or any seeded data):

1. **Does the `_compartment=%clinicAccount` criteria actually deny cross-clinic Patient/Encounter/etc. reads for a staff member who *does* have the `clinicAccount` parameter, inside this box's `superAdmin:true` project?** Source analysis (Task 5/5b) says yes (superAdmin only auto-grants the fixed project-admin-type list, never ordinary resource types); Task 5b proved the mechanism for Practitioner/PractitionerRole masking in a *non-superAdmin* project; nobody has run the clinical-resource version in *this* superAdmin project. This session confirmed the *negative* case (no policy → leaks) but not the *positive* case (policy present → contained) for clinical resources.
2. **Does the `_compartment=%clinicAccount` criteria block `create` of a resource that doesn't yet have `meta.accounts` set (because it was just created and `$set-accounts` hasn't run yet)?** This governs whether every clinical write path (`assignResourceToClinicTenant` is always called *after* `createResource`) will keep working once real staff are migrated onto this policy. Medplum's own docs don't state this explicitly. None of the two currently-"good" local test memberships appear to be the identity e2e actually exercises for clinical writes (`doctor@ucc.local`, the account used throughout `.ai/research/task*.md` and the e2e suite's `UCC_USER`, is one of the two *unpoliced* memberships) — so this specific interaction may be effectively untested in this codebase today, even though the policy script predates this round's work.

Both are answered by one short script (extends `scripts/access-policy/test-nonsuperadmin-containment.mjs`'s pattern, run in *this* project not a disposable one, using fully disposable Organization/HealthcareService/Practitioner/User/ProjectMembership fixtures, never touching real data): create a fake clinic, invite/assign a fake staff member with the real `UCC Clinic Staff Policy` + real parameters, as that fake user (a) try to create a Patient and then immediately read it back, (b) try to read a Patient belonging to a *different* fake clinic. If (b) leaks, phase 1 is blocked pending a different enforcement mechanism (e.g. `_account` legacy field, or an app-level pre-filter as defense in depth — see Security review). If (a) fails, the resource-creation code needs to call `$set-accounts` *before* any subsequent read the same request relies on, or the policy's `create` interaction needs to be granted unconditionally (drop the criteria for `create` only, keep it for read/search/update/delete) — Medplum's `AccessPolicyResource` shape does allow per-interaction-list criteria scoping if needed, but simplest is almost certainly "criteria doesn't gate `create`, only filters what's returned/updatable afterward" (standard REST-criteria semantics), which this test will confirm either way.

## Phase 1 — close the resource-list and stamping gaps (commit 1)

1. `scripts/setup-access-policies.ts`: add `clinicCompartmentRule("Provenance", ["create"])`-shaped entry — **unscoped `create`**, not compartment-filtered, because every clinical write path (`lib/fhir/{lab,imaging,consultation,patient,document}-service.ts`, `lib/fhir/fhir-helpers.ts`) calls `createProvenanceForResource` with the *acting user's* client (not admin), non-blocking try/catch, and Provenance is **currently entirely absent** from the policy's resource list — meaning today, any staff member who *does* have the real policy applied silently loses their entire audit trail on every write (the try/catch swallows the 403). Also add compartment-scoped `read`/`search` for Provenance once phase 1.2 stamps it, so staff can see their own clinic's audit history without leaking others'.
2. `lib/fhir/provenance-service.ts`: `createProvenanceForResource` gains an optional `clinicTenant`/`accountReference` param; when supplied, call `assignResourceToAccountReferences` after create (mirrors every other resource). Thread it through from the ~9 call sites (`lab-service.ts:118,231,252`; `imaging-service.ts:159,251,332`; `consultation-service.ts:486`; `patient-service.ts:401,435,468,499`; `fhir-helpers.ts:46,102`; `document-service.ts:95`) — all already have a `clinicId`/`clinicTenant` in scope at the call site, so this is plumbing, not new resolution logic.
3. `lib/fhir/triage-service.ts`: the three Encounter *update* paths that currently call only `withClinicIdentifier` (around lines 435, 605, 686) also call `assignResourceToClinicTenant` (idempotent — `assignResourceToAccountReferences` already dedupes existing account refs, `clinic-tenancy.ts:205-208`), so an Encounter touched only via these paths ends up with `meta.accounts` too.
4. New script `scripts/access-policy/backfill-clinic-accounts.mjs` (not `backfill-clinic-identifiers.ts`, which only ever sets `identifier` — leave that one as-is, it's used for the app-level identifier/display path and still has value for that): for every resource type in `setup-access-policies.ts`'s `clinicCompartmentRule` list, find resources with **no `meta.accounts`** but a resolvable clinic (reuse `backfill-clinic-identifiers.ts`'s exact inference chain: own `identifier:clinic|<id>` → `managingOrganization`/`serviceProvider` → `encounter`/`basedOn`/`imagingStudy` reference walk → `patient`/`subject` reference walk), and call `$set-accounts` (via `getAdminMedplum()`, `propagate:true` where the resource is a Patient) for the resolved `HealthcareService`. Dry-run by default (`APPLY=true`), same `unresolved` reporting as the existing script, same localhost-only guard pattern as `scripts/access-policy/apply-local-staff-policy.mjs`. **Does not touch `identifier`** (orthogonal to the existing backfill script, can run either order, either independently).
5. `lib/fhir/admin-service.ts`: `updatePractitionerFromMedplum` (~line 600-655), after syncing `PractitionerRole` create/delete to match `input.organizationIds`, also re-derive and re-apply the full multi-clinic `ProjectMembership.access[]` set (one entry per **current** `organizationIds`, dropping entries for organizations no longer assigned) via the same `getClinicPolicyParameters`/`withClinicMembershipAccess` helpers already used by invite — so clinic reassignment can never leave a stale or missing policy parameter.

Gate: lint/build/`e2e/scripts/check-all.sh task-isolation-1` with the current baseline staff accounts (none yet migrated to the real policy — this phase only adds plumbing + a new script, doesn't change who gets the policy, so it should be a no-op for existing behavior; the new backfill/accounts script is dry-run only until phase 2).

## Phase 2 — migrate existing memberships (commit 2, the actual security fix)

New script `scripts/access-policy/migrate-staff-to-clinic-policy.mjs`, same shape/safety rails as Task 5's `apply-local-staff-policy.mjs` (dry-run default, per-membership JSON backup to `/workspace/ai-logs/.../backup/` outside the repo before any write, `--rollback`/`--rollback --apply`, exclusive lock file, refuses to touch a membership that already has *any* non-empty `access`/`accessPolicy` unless it's exactly the expected clinic policy — i.e. it only *adds* the clinic policy to the 2-of-10 local memberships that currently have none, it does not overwrite memberships that already have the directory-containment policy from Task 5 or anything else someone set by hand):

1. For each non-admin `ProjectMembership` with **no `accessPolicy` and no `access`** (today: `doctor@ucc.local` + 1 other, found via the same `auth/me`-independent read used in Task 5b, never an email search): resolve its `Practitioner`'s `PractitionerRole[]` → set of `Organization` ids → build one `access[]` entry per organization via `getClinicPolicyParameters` + the real `UCC Clinic Staff Policy` id (same helpers `admin-service.ts` already exports/uses internally — this script can import and call `getClinicPolicyParameters`/`withClinicMembershipAccess` directly rather than reimplementing them, keeping one source of truth).
2. Run `scripts/access-policy/backfill-clinic-accounts.mjs --apply` (phase 1's script) **before** flipping any membership, so newly-restricted staff don't immediately lose access to their own clinic's older resources that predate `meta.accounts` stamping.
3. Apply one membership at a time, verify with a disposable re-login-equivalent check (reuse the `doctor@ucc.local` + known local test password pattern already used by `e2e/`) that the now-policied account can still: log in, see its own clinic's patients/encounters/orders, and **cannot** see another clinic's. Stop and roll back that one membership (not all of them) on first failure.
4. Repeat for every remaining non-admin membership across all 4 seeded clinics (Task 2's `demo`/`clinicb`/`clinicc`/`clinicd`).

This is the step that actually closes the leak — phases 0/1 are prerequisites, phase 2 is the fix.

## Phase 3 — defense in depth (commit 3, optional but recommended by Security review below)

Per OWASP's Authorization Cheat Sheet ("never rely on client-side access control checks... validated on every request... in multi-tenant contexts, never trust tenant IDs supplied by clients") and the fact that several `getAdminMedplum()` call sites (`lib/models.ts`, `app/api/settings/*`, `app/api/suppliers/*`, `app/api/catalogs/*`) read/write with the *service* client, which has no `AccessPolicy` at all (it's the Medplum client-credentials app) and currently applies **no app-level clinic filter** at all for several of these — add an explicit app-level clinic check in those routes/services as a second, independent layer, so a single Medplum policy misconfiguration (or a future regression in phase 2's migration) doesn't become a silent full reopen. This is not a substitute for phases 1-2 — Medplum's own policy engine remains the primary control for anything reachable by a user's own token — but matches the existing pattern the code already uses in a few places (`getTriageQueueForToday`'s explicit "Always scope by clinic... return empty rather than risk a cross-clinic leak" comment, `triage-service.ts:759-765`) and should be applied consistently to the admin-client call sites that currently have no clinic filter at all, listed in the file-by-file table below.

## Routes/paths that must keep working, explicitly checked

- **Admin/service-client paths** (`lib/server/medplum-admin.ts:getAdminMedplum`): unaffected by phases 1-2 (no `AccessPolicy` on the service client; it's a separate credential, not touched). Phase 3 adds app-level filtering to specific routes, not a Medplum policy change — zero risk of breaking the admin portal's cross-clinic views (clinic list, platform settings) which are *supposed* to see everything.
- **Lab/POCT/X-ray receive routes** (`app/(routes)/api/labs/receive/route.ts`, `.../imaging/receive/route.ts`, `.../labs/receive/message/route.ts`): use `getAdminMedplum()` (confirmed, `lab-service.ts:receiveLabResults`/`imaging-service.ts:receiveImagingStudy` take whatever client is passed, callers pass the admin client) — **not touched by this plan**, continue to work exactly as today. The pre-existing, separately-tracked BACKLOG gap ("shared device key today can write into any clinic") is a different problem (device identity, not staff identity) with its own prerequisite (per-clinic device keys) already noted in `.ai/BACKLOG.md:12` — out of scope here, but flagged so nobody assumes this plan fixes it.
- **Module toggle** (`lib/module-registry.ts`, `lib/module-settings.ts`): reads the clinic `Organization` via the admin client, independent of `AccessPolicy`/`ProjectMembership` — zero interaction with this plan.
- **Bots/Subscriptions**: none exist in this codebase today (confirmed by search) — the "Bot-shaped" POCT bridge (`lib/poct/analyser-bot.ts`, Task 10) is an in-process module invoked by a route using the admin client, same as the receive routes above. Nothing to change.
- **Multi-clinic staff**: `assertClinicAssignment` (app-level, `PractitionerRole`-based) and the new multi-entry `ProjectMembership.access[]` (Medplum-level) are two independent checks answering two different questions and must both be kept correct per clinic — phase 1.5 (`updatePractitionerFromMedplum` re-sync) is exactly this.

## e2e tests to add

Extend `e2e/scripts/clinic-check.ts` (currently only checks Organization count + Patient identifier uniqueness) to also assert, for every resource type in the policy's `clinicCompartmentRule` list: exactly one `meta.accounts` entry resolving to a known clinic `HealthcareService` (read-only, admin client, matches its existing style/exit-code convention).

New `e2e/tests/clinic-isolation.spec.ts` (direct-FHIR, not through the Next app, mirroring `test-nonsuperadmin-containment.mjs`'s assertion style — status/count/boolean only, never print resource bodies):

- For **every** clinical resource type in the policy (Patient, Encounter, Observation, Condition, Procedure, MedicationRequest, MedicationStatement, AllergyIntolerance, ServiceRequest, DiagnosticReport, ImagingStudy, DocumentReference, Appointment, Invoice, Task, ChargeItemDefinition, Communication, QuestionnaireResponse): as clinic-A staff, `read` a known clinic-B resource ID directly against `:8113` → must be 403 or (for search) must return 0 matching entries; repeat the search variant with `_count` high enough to rule out pagination hiding it.
- Across **all 4 seeded clinics** (`demo`/`clinicb`/`clinicc`/`clinicd` from Task 2's seed), not just a 2-clinic pairwise check — pick one resource per type from each of the other 3 clinics when testing from any one clinic's staff account, so a transitive/ordering bug (policy checks clinic A against B but not C) can't hide.
- A multi-clinic staff fixture (PractitionerRole in 2 of the 4 clinics) must see **both** clinics' data and still not see the third/fourth — directly exercises the multi-entry `access[]` union.
- A positive-path regression check: the same staff account can still create a Patient, check in, run a consultation, sign, order a lab/POCT test, and read it back — i.e., phase 0's "does create work under compartment criteria" question gets a permanent regression test, not just a one-off manual check.
- Provenance: confirm creation still succeeds (no more silent audit-trail loss) after migration.

## Rollout / rollback

- Phases 0-1 are additive/dry-run only — no staff lose or gain access; safe to land independently of 2-3 and gate normally.
- Phase 2 (the actual migration) runs **once per membership**, backed up first (private, outside-repo, 0600/0700, exact pattern Task 5 already used and had independently reviewed), with a per-membership `--rollback --apply` that restores the original `accessPolicy`/`access` fields exactly. Roll out clinic-by-clinic or even staff-by-staff, not as one big-bang write, so a single bad case is cheap to revert and doesn't block the rest.
- If phase 0 finds the compartment criteria does **not** hold under this box's `superAdmin:true` project (the one real open risk), **stop** — do not proceed to phase 2 with a policy that's been shown not to work; escalate to the user about either (a) moving local dev to a non-superAdmin project (D20's standing recommendation, already true for intended production per the same decision) or (b) an app-level pre-filter as the *primary* control instead of defense-in-depth, which is a materially different and larger change than this plan.
- Before any phase-2 write in production (not this plan's job — AGENTS.md: agents never touch production): confirm production's project `superAdmin` flag with the user first (D20, still open, Hostinger-boundary).

## Risks

- **Phase 0's two open questions are the crux of the whole plan's validity** — if either comes back negative, phases 2-3 need rethinking before any real migration. Treat phase 0 as a hard gate, not a formality.
- **`meta.accounts` backfill touches every clinical resource** — even read-only `$set-accounts` calls are still writes (they set metadata); run against a fresh local backup, verify counts before/after, same caution as Task 2's seed script.
- **Silent audit-trail loss is already happening today** for the 4 already-policied local memberships (Provenance absent from the policy) — this plan fixes it, but until phase 1 lands, don't assume Provenance records exist for anything created by those 4 accounts.
- **Admin-client routes with no app-level clinic filter** (phase 3's list) are a pre-existing gap independent of the AccessPolicy fix — a determined attacker with access to trigger those specific admin-client-backed routes (not a direct FHIR call, an app route) could still cross clinics there even after phases 1-2. Phase 3 is not optional busywork; it's closing a real, separate hole that phases 1-2 don't touch.
- **Staff member deletion / `deletePractitionerFromMedplum`** cleans up `PractitionerRole` and `ProjectMembership` (confirmed, `admin-service.ts:~664-720`) but wasn't checked in this session for whether it also needs any `access[]`-specific cleanup — likely fine since deleting the whole `ProjectMembership` removes `access[]` with it, but worth a one-line confirmation in phase 2's own testing rather than assuming.
- **Out of scope, do not let this plan's existence imply it's handled**: the shared-device-key cross-clinic write gap (BACKLOG, separate prerequisite), and the superAdmin production-boundary question (D20, Hostinger, user's call).

## Security review (self-critique pass, as a reviewer independent of the plan above)

**MAJOR**

1. **Phase 0 is advisory, not enforced.** As written, nothing stops an implementer from skipping straight to phase 2 "because the policy script already exists." Revision: phase 2's migration script itself should refuse to run (hard-coded check, not just a doc instruction) unless a marker/flag proving phase 0's disposable test passed is present — e.g. require `--phase0-verified=<timestamp>` or read a small JSON result file the phase-0 script writes on success, same spirit as the existing scripts' `--apply` gate. *(Revision applied: added to phase 2's description above — "stop and escalate" language strengthened; recommend the actual implementation task hard-code this rather than rely on operator discipline.)*
2. **The plan assumes `createProvenanceForResource`'s callers all have a `clinicTenant`/`clinicId` in scope, but this wasn't verified for every one of the ~9 call sites, only spot-checked for `lab-service.ts`.** If even one call site (e.g. inside `fhir-helpers.ts`, a shared low-level helper that might be called from a context without clinic context) doesn't have it, that call site either needs its own clinic resolution or the Provenance fix needs to tolerate a missing account reference (fall back to unscoped `create`, same as today, rather than start throwing). Revision: phase 1's Provenance change must keep the account parameter *optional* and *non-fatal* if absent (log once, don't throw) rather than assume it's always derivable — this is already implied by "optional param" above but should be stated as a hard requirement, not an implementation detail.
3. **No verification in this research session that the "2 non-admin memberships with no policy" are actually only test/seed accounts and not something a human administrator intentionally left unpolicied for a reason** (e.g. a break-glass admin-adjacent account). Revision: phase 2's script must print (not act on) the `Practitioner.name`/role context for operator review before the first real `--apply` in each environment — not blind automation, matching Task 5's own "require existence as well as allowed accounts" caution about blind backfills.

**MINOR**

4. The plan's e2e test list says "every clinical resource type in the policy" but doesn't pin an exact count/list the way `scripts/clinic-check.ts` pins "4 clinics" — a future edit to `setup-access-policies.ts`'s resource list could silently stop being covered by the new e2e test. Revision: the new test should import/derive its resource-type list from the same source `setup-access-policies.ts` uses (export the list, don't hand-copy it into the test file), so they can't drift.
5. Phase 3's admin-client app-level filtering list was built from the earlier Explore-agent inventory pass and spot-checked for only 2-3 of the named files (`lib/models.ts`, `admin-service.ts`); the others (`app/api/settings/*`, `suppliers`, `catalogs`) were not individually re-read in this session, only taken from the agent's summary. Revision: flag this explicitly (done, this line) and require the implementing task to re-verify each file:line before writing code, not trust the inventory pass verbatim — agent-produced inventories in this session were spot-checked and found accurate where checked (the `setup-access-policies.ts`/`admin-service.ts` existence was the single most consequential claim and was independently verified by direct file reads), but phase 3's specific list was not re-verified to the same standard.
6. "`_compartment` search parameter" was confirmed to work for an **admin/superAdmin** client in this session's diagnostic; it was not independently reconfirmed that the search parameter itself (as opposed to the AccessPolicy criteria *using* it) behaves identically for a restricted client — low risk (search parameter registration is server-wide, not per-policy), but noted for completeness.

No findings were dropped as out-of-scope-and-therefore-ignored; the BACKLOG/D20/Hostinger items are explicitly carried forward as named risks rather than silently dropped.
