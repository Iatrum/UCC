## Decision

Use BOTH policy and application checks. Keep criteria for reads. For patient-linked creates use a writeConstraint requiring nonempty server-computed accounts and every account to match the server-derived assigned-clinic union. Update/delete additionally use the installed resource-level compartment field to select an existing authorized record. All access entries carry the same anchored, escaped clinicWriteAccounts regex; single-clinic grants without that new parameter retain an exact clinicAccount fallback. This avoids the first-rule problem of adding writeConstraint to criteria-only compound policy entries. Deny unattached patient-related creates; Patients themselves retain create permission because patient creation precedes server-side account stamping. Standalone clinic configuration types keep their existing behavior. No policy is deployed or real membership changed by this task. Rollout must refresh multi-clinic access parameters with the complete clinicWriteAccounts union BEFORE installing the revised definition; legacy single-clinic memberships work via the exact fallback. Do not install this policy alone over old multi-clinic grants. Task has no Patient compartment in FHIR R4; Task and standalone configuration retain existing behavior, not a claim of whole-policy write isolation.

Provenance cannot validate target ownership with the installed synchronous FHIRPath evaluator. Remove direct staff create permission; the existing server-only helper reads each local target with the acting client's permissions before using the admin client to create/stamp its audit record. Never fall back to privileged target reads on denial. This addresses the independent review's unscoped Provenance finding too.

App order services additionally validate the Patient and optional Encounter against the selected clinic and each other before the first create, including for an unrestricted/admin client. Existing consultation/triage paths already check their patient clinic. No device-key redesign, migration, backfill apply, module or navigation work is included.

Validation and limitations will be appended after live disposable tests. Deprecated resource-level compartments are deliberate version-specific compatibility; re-verify before any Medplum upgrade. Policies only protect memberships using them; missing-policy migration is still Phase 2.

### Confirmed SDK correction and policy tradeoff

The official v5.1.13 client.ts downloaded on resume exactly matches the installed source map (byte comparison). It DOES expose extendedMode (default true) and defaultHeaders. Earlier Phase 1/research assertions that the SDK has no extended option or that plain admin clients always hide accounts are inaccurate. We still explicitly request X-Medplum: extended plus cache:no-cache at the three reuse reads, so correctness holds for non-extended clients and previously cached plain reads too. This is scoped per request, with no singleton/global mutation.

In this privileged project, CREATE readonlyFields:[meta] strips user-supplied profile/tag/security metadata as well as forged accounts. Clinical fields are retained; existing metadata is restored on UPDATE. The server computes its own audit/project/compartment metadata. This is a deliberate version-specific integrity tradeoff; deploy only after review, and re-evaluate when moving staff to a non-superAdmin project or upgrading Medplum. No project topology/settings change is included.
