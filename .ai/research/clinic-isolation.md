## tl;dr — the premise needed correcting

The task brief ("AccessPolicy clinical grants have no clinic criteria") is **not quite what's in the repo**. There is already a working, parameterized, compartment-based AccessPolicy for exactly this purpose — `scripts/setup-access-policies.ts` + `lib/fhir/admin-service.ts:42-100` (`getClinicPolicyParameters`, `withClinicMembershipAccess`) — and it **is** wired into the staff-invite path (`invitePractitionerToMedplum`, `admin-service.ts:880-910`). The actual bug is that the rollout is incomplete in three independent ways, each confirmed empirically on this box today:

1. **Not every staff `ProjectMembership` has the policy.** Of 10 non-admin+admin memberships, 2 non-admin ones have **no `accessPolicy` and no `access[]` at all** — including `doctor@ucc.local`, the exact account Task 5's research used. A membership with neither field gets Medplum's legacy full wildcard grant (Task 5 research, point 4). Confirmed live: logged in as `doctor@ucc.local` and did a plain `readResource('Patient', <id>)` and a `searchResources('Patient', {_count:500})` for a patient that belongs only to a different clinic's `HealthcareService` — **both succeeded**, returning the other clinic's patient. This is the leak, reproduced today, not merely inferred from Task 5's notes.
2. **`meta.accounts` (the field the `_compartment=%clinicAccount` criteria actually matches on) is only partially stamped.** Patient: 20/20 sampled had `meta.accounts` set. Encounter: only 9/20 sampled did. Root cause traced to `lib/fhir/triage-service.ts`: the Encounter *create* paths (lines ~480, ~554) call `assignResourceToClinicTenant` (which does `$set-accounts`), but three Encounter *update* paths (lines ~435, ~605, ~686) call only `withClinicIdentifier` (sets the app-level `identifier: clinic|<slug>` field, not `meta.accounts`). An Encounter with no `meta.accounts` won't match `_compartment=%clinicAccount` for *either* clinic — it fails closed for properly-policied staff rather than leaking, but it means the compartment criteria can't be trusted to cover 100% of Encounters without a backfill + a code fix.
3. **Reassigning a practitioner to a different clinic via the admin UI doesn't update their access policy.** `updatePractitionerFromMedplum` (`lib/fhir/admin-service.ts:~600-655`) syncs `PractitionerRole` create/delete to match the admin's chosen `organizationIds`, but never re-calls `getClinicPolicyParameters`/`withClinicMembershipAccess`. So the *app-level* "which clinic can this user operate as" check (`assertClinicAssignment`, which reads `PractitionerRole`) and the *Medplum-level* "which clinic's data can this user's token actually read" check (`ProjectMembership.access[]`, set once at invite time) can drift apart after any reassignment.

None of this requires inventing a new data model or policy language — it requires **finishing the existing one** (migrate every existing membership, backfill every resource's `meta.accounts`, fix the three update-path gaps, keep the policy in sync on reassignment) plus closing a couple of adjacent gaps found while reading the code (below). This materially changes the shape of the plan in `.ai/PLAN-clinic-isolation.md` from Task 5's "design a tenant policy from scratch" framing to "complete and verify an unfinished rollout, with a migration script."

## Local superAdmin project — still true, now more precisely scoped

Confirmed again today: local project `superAdmin=true` (admin `auth/me`). Per Task 5/5b's own source-verified finding (`fa6bada` commit of `packages/server/src/fhir/accesspolicy.ts`, `applyProjectAdminAccessPolicy`), superAdmin only auto-grants the fixed list of **project-admin resource types** (`AccessPolicy, Cron, Package, PackageRelease, PackageInstallation, Project, ProjectMembership, User, UserSecurityRequest`) — never Patient/Encounter/etc. `supportsInteraction`/`canPerformInteraction` (`repo.ts`) still evaluate the assembled policy, including parameterized `_compartment` criteria, for ordinary resource types regardless of superAdmin. Task 5b independently proved the `_compartment`-style masking mechanism works end-to-end (29/30 assertions, Practitioner/PractitionerRole telecom) **in a non-superAdmin test project**.

**Gap not closed by this research session:** nobody has yet run the equivalent of Task 5b's disposable-identity test for an *ordinary clinical resource type* (`clinicCompartmentRule("Patient")`) specifically inside this box's superAdmin project — i.e., prove that a staff member who **does** have the `clinicAccount` parameter correctly gets denied cross-clinic Patient access, not just that one with **no policy at all** leaks (which this session did confirm). The source analysis strongly predicts it will work identically to the non-superAdmin case, but it hasn't been measured. The implementation plan below makes this its first verification gate, before touching any real membership.

## Official sources consulted (this session, in addition to the full list already in `.ai/research/task5-access-policy.md`, not re-copied here)

- Medplum multi-tenant access policy guide (parameterized `%variable` substitution, `access[].parameter`, union/combine semantics for multiple `access[]` entries per membership — "This pattern scales to any number of tenants per user"): https://www.medplum.com/docs/access/multi-tenant-access-policy
- Medplum `$set-accounts` operation (sets `meta.accounts`; `propagate:true` cascades to the Patient compartment, ≤1000 resources, needs explicit permission): https://www.medplum.com/docs/api/fhir/operations/set-accounts — matches what `clinic-tenancy.ts:221` already does.
- FHIR R4 search — `_compartment` and general search parameter semantics: https://hl7.org/fhir/R4/search.html. Confirmed live against the running server (`_compartment=HealthcareService/<id>` is a recognized search parameter here; `_account` is **not** — a wrong guess during this session's own diagnostic script, corrected).
- OWASP Authorization Cheat Sheet (IDOR / multi-tenant object-level authorization): deny-by-default, "permission should be validated correctly on every request... regardless of whether initiated by an AJAX script, server-side, or any other source," never trust client-supplied tenant identifiers, add unit/integration tests specifically for authorization logic. https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html
- OWASP Top 10:2021 A01 Broken Access Control (category this bug falls under — cross-tenant read of another organization's records via a missing per-record server-side check): https://owasp.org/Top10/A01_2021-Broken_Access_Control/
- Malaysia PDPA 2010 (Act 709), Security Principle ("Prinsip Keselamatan"): requires taking steps so personal data is secure, not altered, not misused, and **not disclosed to parties that are not relevant/authorized** ("tidak diberikan kepada pihak-pihak yang tidak berkenaan"). https://www.pdp.gov.my/prinsip-perlindungan-data-peribadi/ — directly supports treating a same-company, different-clinic staff member as an unauthorized party for another clinic's patient data (need-to-know, not just "any logged-in staff").

## What this changes in the plan vs. Task 5's framing

- No new resource type or tenant model needed — reuse `Organization`/`HealthcareService`/`clinicAccount` exactly as already coded.
- No new AccessPolicy JSON needed from scratch — extend `scripts/setup-access-policies.ts`'s existing `CLINIC_POLICY_NAME` resource list (a few resource types created by services are missing from it — see plan's gap table) rather than write Task 5's separate `ucc-local-staff-containment.json` (that one only ever addressed the ProjectMembership/Practitioner *directory* leak, explicitly not cross-clinic clinical data; it should be supersede-able once every membership has the real clinic policy, since the real policy's own omissions already deny ProjectMembership/User/Project/AccessPolicy by the same "unlisted type = no grant" rule, and additionally scope Practitioner/PractitionerRole/Organization/HealthcareService to read-only + clinic criteria rather than Task 5's blunter "readonly + hidden telecom, project-wide").
- The actual implementation work is a **migration** (every existing membership + every existing resource) plus **two code fixes** (triage-service.ts update paths; `updatePractitionerFromMedplum` re-syncing `access[]`), not a from-scratch architecture change. This is a smaller, lower-risk change than Task 5 anticipated, but the migration script touches every clinical resource in the database and every staff login, so it still needs careful phasing, dry-runs, and rollback — detailed in `.ai/PLAN-clinic-isolation.md`.

## Phase 0 results (2026-11-10, empirical, Task 090) — both questions answered, plus one new finding

Script: `scripts/access-policy/test-clinic-policy-superadmin.mjs`. Disposable `Organization`/`HealthcareService` x2 (clinics A/B), one disposable `Practitioner`/`User`/`ProjectMembership` ("staffA") invited and then assigned the **real** `UCC Clinic Staff Policy` (`AccessPolicy/58aa5927-...`, read-only reference, never modified) with real `clinicAccount`/`clinicOrganization` parameters pointing at disposable clinic A, exactly the shape `admin-service.ts`'s `withClinicMembershipAccess` produces at invite time. Two disposable `Patient`s (A1 in clinic A, B1 in clinic B) created via the admin client and stamped with `$set-accounts`, mirroring the app's real `assignPatientToClinicTenant` flow. Everything torn down in a `finally` (teardown log: all `status=200/204`, nothing untracked). Note: the real `UCC Clinic Staff Policy` did not exist in this project at script start (local Medplum was restored from a 6 Nov backup on 8 Nov, pre-dating this policy or losing it in the restore) — ran `bun scripts/setup-access-policies.ts` first (idempotent upsert by name, additive, matches what already runs in every environment's setup) before the disposable-identity test. Full per-assertion table in `/workspace/ai-logs/task90-phase0/evidence.txt`.

**Q1 (does `_compartment=%clinicAccount` deny cross-clinic reads for a policied account inside this box's `superAdmin:true` project, for ordinary clinical resources) — CONFIRMED YES**, closing the one gap Task 5b's own research left open (it only proved the mechanism for the Practitioner/PractitionerRole *directory* case, in a *non-superAdmin* project):
- staffA direct `GET Patient/<A1>` (own clinic) → `200`.
- staffA direct `GET Patient/<B1>` (other clinic) → **`404`**, not `403`. Traced in the live `medplum/medplum-server:latest` container's bundled `@medplum/server/dist/index.js` (`docker exec uccmp-medplum-1 node -e ...`, read-only, no write): `readResourceFromDatabase` applies the access-policy criteria as a SQL `WHERE` predicate (`addAccessPolicyFilters`) on the *same* query that fetches the row — a non-matching row is indistinguishable from a nonexistent one, so Medplum returns "not found," not "forbidden," for a direct read outside the compartment. Any future e2e/app code asserting cross-clinic denial must check for `404`, not `403`, on direct reads (search already correctly returns `200` with the row simply absent from the Bundle).
- staffA `Patient?_count=200` search → contains A1, never B1.

**Q2 (does the criteria block `create` before `$set-accounts` has run) — CONFIRMED NO, it does not block create.** This is better news than the plan assumed necessary to check for safety, not worse:
- staffA raw `POST Patient` (no `meta.accounts`, nothing to inherit from) → `201`, and an immediate `GET` of that same resource by staffA → `200`.
- staffA `POST ServiceRequest {subject: Patient/A1}` (the exact shape `createLabOrder` uses with the caller's own token, confirmed by reading `app/(routes)/api/labs/order/route.ts` — lab/imaging/consultation-sign routes pass the user's own `requireClinicAuth` client, not the admin client, unlike `savePatientToMedplumWithAdmin`/`lib/models.ts:createPatient`, which both always use `getAdminMedplum()`) → `201`, immediate `GET` by staffA → `200`.
- staffA `POST Observation {subject: Patient/A1}` → `201`.
- **Conclusion: migrating staff to the real policy (phase 2) will not break Patient creation (admin-client path, unaffected either way) or the consultation/lab/imaging order-creation paths that do run on the staff member's own token** — phase 0's blocking concern does not materialize. No "drop criteria from `create` only" policy change is needed.

**New finding, not one of the plan's two original questions — write-side cross-clinic containment gap (document, do not fix in this task):**
- staffA `POST Observation {subject: Patient/B1}` (a patient in the *other* disposable clinic, which staffA cannot even read — confirmed `404` two assertions earlier in the same run) → **`201`, not the expected `403`.** staffA can create a new clinical resource attached to a patient they are not permitted to read.
- This is consistent with the Q2 result above (the criteria plainly does not gate `create`) but has a different, more serious implication when the referenced patient belongs to *another clinic*: a staff member can attach new data to a patient record they cannot see. They could not read it back afterward (the new resource inherits patient B1's own account via Medplum's `getAccounts()` patient-compartment inheritance, confirmed by source read of the live container's bundled `repo.ts` logic — not independently re-verified this session by trying to read staffA's own B1-linked Observation back as staffA, left as a documented gap in this test's own coverage), so this is not a read/exfiltration vector, but it is a genuine OWASP A01 Broken Access Control defect: cross-tenant object creation, which could corrupt or spam another clinic's patient record (data integrity / limited DoS), and plainly fails a strict reading of "clinic data stays separate."
- **Root cause is two-layered, confirmed by reading both layers:** (1) Medplum's own criteria-matching for `create`/`update` (`satisfiedAccessPolicy`/`matchesAccessPolicyResourcePolicy`) did not deny it either, per the Q2 evidence above — the per-resource `criteria` string does not appear to gate write interactions the way it gates read/search in this version; (2) independently, at the **application** layer, `createLabOrder` (`lib/fhir/lab-service.ts:68-130`) and `createImagingOrder` (`lib/fhir/imaging-service.ts`) never validate that `order.patientId` belongs to the caller's own `clinicId` before building `subject: {reference: Patient/<id>}` and calling `createResource` — unlike several *read*/*update* paths in `patient-service.ts`/`triage-service.ts` that do call `assertMatchesClinic`/`matchesClinic` first. Today, with only 4/10 local memberships even policied, this is already a live, exploitable gap for any staff member who already has the real policy, pre-existing and independent of this task's phase 1 work.
- **Not fixed in this task** — phase 1's scope (per the task brief) is plumbing only (Provenance rule, provenance stamping, triage update-path stamping, dry-run backfill, `access[]` re-derive), not new authorization logic, and this finding deserves its own reviewed task (add an `assertMatchesClinic(patient, clinicId)`-style check immediately after resolving `order.patientId` in every order-creation service function, before `createResource`, as an app-level fix independent of whatever Medplum's `AccessPolicy` engine does or doesn't enforce on write). Recorded in `.ai/BACKLOG.md` and flagged as a MAJOR finding in `.ai/REVIEW-task-isolation-1.md` so it isn't lost before phase 2 (real migration) proceeds.
