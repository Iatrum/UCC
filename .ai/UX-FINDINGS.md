## Scope not covered this pass
Composer/Lab-tab/checkout deep screens weren't exercised live: the dashboard queue had 0 patients "waiting for consultation" (all were already at "Meds & Bills" billing status), so there was no in-progress consultation to open read-only within the 25-minute timebox. `/orders/checkout` 404s without a `patientId` query param, which is expected (not meant to be deep-linked). Re-run with a seeded "waiting" patient to audit the composer and Labs & Imaging tab rendering directly.

## Top 5 quick wins
1. Put Dashboard, Patients, and Orders/Billing back into the persistent sidebar as labelled links — they're the doctor's most-used pages and currently cost a URL guess or an icon guess (#1).
2. Replace the dashboard's infinite "Loading queue…" with a timeout + error/retry state, and don't let the sidebar show "Login" while the page thinks it's authenticated (#2).
3. Redirect disabled-module routes (POCT/PACS/Tasks/Records) to a friendly in-app message instead of the bare Next.js 404 (#3).
4. Default the Document Templates editor to live Preview and add a confirm step before saving raw HTML that drives every printed MC/referral letter (#4).
5. Fix DOB/date inputs to an unambiguous `dd/mm/yyyy` format to match the NRIC convention used everywhere else in the app (#5).

Interaction counts observed (excluding typing/scrolling): queue row menu → Start Consultation → Start consult = **3 clicks** to reach the notes editor; diagnosis by mouse = **2 clicks** (open + result); keyboard attempt = **1 click + typing + ArrowDown + Enter**, with the incorrect free-text selection above; Lab tab = **1 click**, stale-report recovery = **2 tab clicks**. Picker counts and treatment autosave messages are unmeasured because of the sign gate. Notes entry is one editor click plus typing; no autosave indicator appeared. For an ED doctor the priority is trustworthy results/error states and draft retention, then tablet legibility and keyboard reliability.

Performance: observed registration submit **5.76s**, check-in through visible queue row **5.78s** (>3s); diagnosis search **1.80s**, populated Lab-tab click through visible haemoglobin **0.89s**, initial registration navigation **2.61s**. These are single-run dev-server end-to-end timings, not production benchmarks; no repeated percentile claims. Queue start/initial profile loading were not separately timed. Lab loading uses a skeleton; the successful fetch resolved without an observed >3s stall. Normal/high results have both icons and text, so interpretation is not color-only. No genuine console/page errors were observed in the exercised happy path; the only recorded console errors/HTTP failures are from the deliberately injected Lab 500 (development mode made two failed requests). Earlier `facts.json` entries retain the previous step label; both pairs belong to that injection.

Validation was the live browser audit and inspection of its screenshots/JSON. The full `check-all.sh` gate was **not run**: its global setup logs in and its workflow creates additional patients, signs consultations/treatments and submits billing, conflicting with this audit's one-patient/no-Sign scope.
