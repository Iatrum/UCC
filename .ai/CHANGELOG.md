# CHANGELOG (plain language)

## 2026-11-17 — Task 452: dashboard queue keeps its list while refreshing
The dashboard queue used to swap the whole list for "Loading queue..." on every refresh (including the 30-second auto refresh), and if you clicked away while it was loading, the interrupted request showed up as a "Failed to load" error. Now "Loading queue..." only appears the first time; later refreshes keep the current list on screen. If a refresh fails, the list stays and the "Queue could not be refreshed" banner appears; the full error panel with Retry only shows when there is no list yet. Requests cancelled by leaving the page (or replaced by a newer refresh) no longer show errors; a real 10-second timeout still does. The same quiet handling applies to Appointments and Billing. Left for Hidayat: the nav label that reads "Login" instead of "Logout" while the session loads (no sidebar/nav changes in this task). Tests: extended `e2e/tests/dashboard-load-errors.spec.ts`.

## 2026-11-17 — Task 430: dashboard Billing and Appointments tabs show loading and errors
The dashboard Billing tab used to say "No billable consultations found" when the billable list failed to load (and while it was still loading), even though /orders listed a billable patient. It now shows "Loading billable consultations..." while fetching, and "Failed to load billable consultations." with a Retry button if the request fails; the empty text only appears after a successful fetch that returned nothing. The dashboard Appointments tab got the same treatment ("Failed to load appointments." + Retry). Same pattern as the queue. No composer, sidebar or navigation change. Test: `e2e/tests/dashboard-load-errors.spec.ts` (mocked failure, then Retry shows the list).

## 2026-11-16 — Task 354: composer never says "saved" when the server refused the save
The "Unable to detect a Project Id" error came from the old Firebase-backed plan store; since the U1b draft retention work, `/api/consultations/plan` stores drafts in Medplum, and on the dev Medplum a real add, reload and read-back works with no Firebase credentials. What remained was in the composer: it guessed "the server can't store drafts" from error text (`UNAUTHENTICATED`, "Project Id") and quietly switched to on-screen-only mode, and any other failed save made the item vanish. Now only an explicit `persistenceAvailable:false` from the server means on-screen-only. Any other rejection (401, 403, 409, 500, network) shows "Failed to save" with Retry, keeps the doctor's item on screen, and keeps Sign disabled until it is saved or removed. Removing an item whose save failed clears the failure. No change to the server route, Firebase Storage, Lab/POCT or navigation.

## 2026-11-16 — Task 357: X-ray phase 3 (real DICOM storage + viewer, dev only)
A dev-only PACS (Orthanc for storage, OHIF as viewer; compose project `ucc-pacs-dev` in `infra/pacs-dev/`) now feeds UCC. When Orthanc has a complete study it notifies UCC with the clinic's per-device key; UCC reads the study back from Orthanc and attaches it to an X-ray order only when the study's accession number matches exactly one open X-ray order of that clinic. ## 2026-11-16 — Task 355: radiology report endpoint no longer fails open
`POST /api/imaging/report` used to accept anyone when `PACS_API_KEY` was unset and never checked the clinic. It now uses the same per-device key as `/api/imaging/receive`: a missing, malformed, unknown, revoked, inactive or wrong-type (POCT) key gets 401; a study (or its originating order) that belongs to another clinic, or a clinic with the PACS toggle off, gets 403. The clinic comes from the authenticated Device and is stamped on the DiagnosticReport; the shared `PACS_API_KEY` is no longer read. Behaviour change for callers: radiology reporting clients must send a per-device key (`Authorization: Bearer` or `X-Device-Key`). No UI change.

## 2026-11-15 — Task 180: per-device keys for analysers and X-ray devices
Each analyser or X-ray device now has its own API key (only a hash is stored on the device record). The four result-receiving routes check that key, work out the clinic from the device itself, and refuse to save a result into another clinic's order. Without a valid key they refuse (401), and they also refuse when the clinic has switched the POCT or X-ray module off (403). The shared `POCT_API_KEY`/`PACS_API_KEY` for these routes is gone, so the JSON routes no longer accept unauthenticated calls. The device simulators gained an `issue-key` command that writes the key to a private file instead of printing it. The radiologist-report route is unchanged and logged in the backlog.

## 2026-10-31 Task 6b – "Too many attempts" no longer shown as "wrong password"
- **What changed:** When Medplum blocks sign-in for a minute (5 tries per IP per minute), the login page now says "Too many sign-in attempts. Please wait about N seconds and try again." instead of "Incorrect email or password". If Medplum is down or answers 5xx it says the sign-in server is busy/unavailable. A real wrong password still shows the same generic message (no hint whether the email exists). The API now returns 429 + `Retry-After` for this case.
- **Why:** Medplum rate limits /auth/login and answers 429 with a `RateLimit: …;t=<secs>` header (medplum.com/docs/rate-limits, checked locally); RFC 6585/9110 for 429 + Retry-After.
- **Please test:** on the login page type a wrong password 6 times quickly -> the 6th shows "Too many sign-in attempts…". Wait a minute -> normal sign-in works.

## 2026-11-04/05 — Task 10: simulated analyser, result bridge, Lab tab pending tests
A new `scripts/poct/sim-analyser.ts` tool can stand in for a real POCT analyser during development: it keeps a test Device's "online" heartbeat going (or lets it go offline), and sends realistic HL7 (ORU^R01) or ASTM (E1394) result messages for a signed POCT order. Those messages are parsed and turned into the same lab result records doctors already see, by a new bridge (`lib/poct/analyser-bot.ts`) written in the shape of a Medplum `Bot` so it can become a real one later, reached today through a new `POST /api/labs/receive/message` endpoint (same device-key check as the existing lab result endpoint). While testing this, also fixed a bug found in the existing `/poct` worklist and the Lab tab's own result lookups: once a clinic or patient has more than 20 lab results or POCT orders, some patient names/results were silently dropped because a database search had no explicit limit (Medplum's default is 20). All four affected lookups now ask for up to 200.
**Why:** FHIR R4 Observation/DiagnosticReport (unchanged shape, reused); HL7 v2.5.1 and ASTM E1394-97 are the two message formats real lab analysers commonly speak. Medplum Bots need a server setting (`vmContextBotsEnabled`) that is not turned on for this shared box, so the bridge logic is written ready to become a real Bot but is not deployed as one yet — see `.ai/progress-task10.md` for the full reasoning.
