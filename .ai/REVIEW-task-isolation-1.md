### Findings

1. **MAJOR (pre-existing, already disclosed, independently confirmed) — write-side cross-clinic creation is not contained.** `clinicCompartmentRule`'s `criteria` (`setup-access-policies.ts`) is granted for `create` alongside read/search, but FHIR/Medplum `criteria` only filters what a request can see/match, not what a `create` body is allowed to reference — confirmed by reading `createLabOrder`/`createImagingOrder` (`lib/fhir/lab-service.ts:146`, `imaging-service.ts:186`) and the new Provenance `create` rule: none of the order-creation paths validate that `patientId`/`subject` belongs to the acting clinic before `createResource`. This PR does not introduce the gap (it predates this diff per Phase 0's own test) and does not widen it materially — correctly scoped as a BACKLOG follow-up requiring its own `assertMatchesClinic`-style check, not a Phase-1 fix. Note for whoever picks up that follow-up: the new unscoped Provenance `create` rule (`setup-access-policies.ts`, this diff) sits in the same category and should be covered by the same fix, not treated as a separate gap.
2. **MAJOR (pre-existing, already disclosed, independently confirmed) — `meta.accounts` is invisible on non-extended reads, so some of this PR's own account-stamping calls are no-ops today.** Traced `imaging-service.ts:216` (`const serviceRequest = await client.readResource(...)`, plain read) → `getResourceAccountReferences(serviceRequest)` → empty array → `assignResourceToAccountReferences(..., accountRefs)` (`clinic-tenancy.ts:206`, unchanged by this diff) returns immediately on `accounts.length === 0`. Same shape at `lab-service.ts`'s `receiveLabResults` Observation/DiagnosticReport calls. This PR's own Phase 1.2 Provenance-account param inherits the same empty value at exactly those call sites (`imaging-service.ts:283,373`, `lab-service.ts:260,287`) — correctly flagged by the author as a no-op there, not a regression. The sites that resolve their own `clinicTenant` directly (`patient-service.ts`, `consultation-service.ts`, `document-service.ts`, `createLabOrder`/`createImagingOrder`'s own order-Provenance calls) are unaffected and do stamp correctly, since they never round-trip through a non-extended read first.
3. **MINOR (new observation, not blocking) — review brief's premise about the installed Medplum version does not hold.** AGENTS.md states "Medplum 5.2.8"; `node_modules/@medplum/core/package.json` and `@medplum/fhirtypes` are both pinned and installed at `5.1.13` (matches `package.json`'s `^5.1.13`), while the plan/self-review docs reference the *server* container as `5.2.15`. All three numbers disagree. Not caused by this task and not a defect in this diff — `createResourceIfNoneExist` (conditional create via `If-None-Exist`) and `executeBatch` with a `transaction` bundle both behave as this PR assumes when checked against the installed SDK source — but AGENTS.md's version string should be corrected separately so future reviews check the right source.
4. **MINOR (new observation, not blocking) — gate is not a clean PASS yet.** The task brief's own evidence (this file, "Validation") is a composite reconstruction (23/24, no new failures) assembled after one real foreground run returned OVERALL FAIL on a composer timing issue. The reasoning that it's a cold-compile timing artifact rather than a Phase-1 regression is well-supported (unchanged-code replay 10/11, same known-bug-only gap), but a single clean `e2e/scripts/check-all.sh` run with a warm dev server has not actually been captured for this diff. Recommend one more clean run before this PR leaves draft, for the record — not required to approve the code itself.
